まずは、原稿＋テンプレート＋デザインの希望。

このマニュアルは lp-template-copy-design を中心に、関連する3つのLPスキルを組み合わせて使う方法をまとめています。すでにスキルを利用できる環境での制作が対象です。

① 内容を決める

誰に、何を、いくらで案内し、どこから予約してもらうかを整理します。

② 見た目を作る

テンプレートへ原稿を配置し、色・文字・写真を整えます。

③ 仕上げて確かめる

スマホとPCで表示・動作を確認し、未設定項目を整理します。

依頼文の［ ］を実際のファイル名や希望に置き換えて使ってください。原稿作成・画像生成・公開は、それぞれ必要に応じて別に依頼する工程です。

WHICH SKILL?

目的に合わせた使い分け

やりたいこと使うスキル受け取るもの
スマホ中心の土台を作るmobile-first-lp-template中央約480pxのLP。PCは左右にナビ・CTA、スマホは下部固定CTA。
原稿・配色を反映するlp-template-copy-designLP一式＋完成LPに基づくデザインシート画像・HTML・設定JSON。
制作済みLPを仕上げるlp-design-final-polish修正したLP、最終チェック結果、修正前後の画像。
品質を点検するlp-quality-checkerリンク・画像・原稿整合性などの検査結果。静的検査と実画面の確認。

すでにテンプレートがある場合は、土台づくりを省いて流し込みへ進みます。品質チェッカーは補助として使えます。仕上げスキルの必須依存ではありません。

WORKFLOW & PROMPTS

制作の進め方

01

材料をひとつのフォルダにまとめる

完成原稿・テンプレート・写真・予約先・デザインの希望を用意します。提供済みの情報は、その場所を指定すれば使えます。

原稿は価格・対象・時間・追加料金・期限まで確定したものを用意。写真は用途が分かる名前にします。未確定項目は「未確定」と明記してください。
02

原稿を流し込み、デザインを整える

lp-template-copy-design を使います。既存テンプレートを複製し、原稿を各セクションに配置して配色・書体・余白を整えます。

デザインは文章・参考画像・記入シートのどれでも指定できます。決められない項目は「おまかせ」と伝えます。写真やFV画像が未完成でも進められます。
コピーして使える依頼文
lp-template-copy-design を使って、LPを制作してください。
原稿：［ファイル名またはフォルダ］
テンプレート：［フォルダまたはZIP］
出力先：［新しく作るフォルダ］
デザイン：［色・雰囲気・参考資料／未定の項目はおまかせ］
写真：［素材フォルダと用途］
CTA文言：［予約する等］
予約URL：［URL／未設定］
原稿・料金・条件は維持し、不明点は捏造しないでください。
スマホとPCで確認し、完成LPに基づくデザインシート画像と設定JSONも出力してください。
03

写真を入れて、実画面を確認する

店内・スタッフ・施術・事例の写真を役割に合わせて配置します。参考デザインの写真やロゴを、そのまま使用素材として流用しないでください。

文字入り画像は全体を表示し、価格や条件を切らないこと。実際のスタッフや施術事例には、使用できる実写真を指定してください。
コピーして使える依頼文
対象LP：［lp/index.html］
素材：［写真フォルダ］
各写真を実際に見て、店内・スタッフ紹介・施術等の役割に合う場所へ配置してください。
原稿・料金・条件を維持し、実績写真とイメージ画像を区別してください。
文字入り画像を切らず、スマホ幅で画像と本文の重複も確認してください。
04

デザインシートを次の制作に使う

design-sheet.png は、完成LPの色・文字・CTA・代表画面をまとめた画像です。FVやオファー画像、別ページの雰囲気を合わせる参照に使います。

入力用のデザイン希望シートとは別物です。正確な色や文字設定は design-tokens.json を参照。LPを変更したらシートとのズレも更新します。
コピーして使える依頼文
対象LP：［lp/index.html］
lp-template-copy-design を使い、既存LPからデザインシートだけを作ってください。
実際のCSS・表示を基準に、design-sheet.png、編集用HTML、design-tokens.jsonを保存してください。
仮画像や未確定事項は、その状態が分かるように記録してください。
05

仕上げと最終チェックを依頼する

lp-design-final-polish を使います。読みやすさ、改行、余白、画像、CTAの見せ方を調整し、スマホとPCの実画面で再確認します。

原稿・価格・ブランド色・採用写真・予約先などは原則維持します。「チェックだけ」と指定すれば編集せず指摘を受け取れます。
コピーして使える依頼文
lp-design-final-polish を使って仕上げてください。
対象LP：［lp/index.html］
正本の原稿：［ファイル名］
デザイン資料：［designフォルダ］
原稿・料金・条件・ブランド色・採用写真・予約URL・計測コードを維持してください。
修正前を復元できる形で残し、余白・文字・画像・CTAを改善してください。
375px程度と1366px程度で表示と動作を確認し、最終チェック結果と修正前後の画像を残してください。
公開はまだ行わないでください。
06

納品物を確認し、公開準備へ進む

LP本体と制作資料を分けて受け取ります。公開用は lp/ の中身です。デザイン資料や内部チェック結果を、顧客向けLPに混ぜないようにします。

制作依頼だけでは公開は行いません。公開を依頼するときは公開先・対象フォルダを指定し、公開後のURLでも表示とリンクを確認します。

納品フォルダの見方

案件フォルダ/
├─ lp/                         ← 公開用のLP本体
│  ├─ index.html
│  ├─ style.css / script.js
│  └─ assets/                   ← 写真・画像
├─ design/                     ← デザイン共有用
│  ├─ design-sheet.png
│  ├─ design-sheet.html
│  ├─ design-tokens.json
│  └─ assets/                   ← シート用キャプチャ
└─ 制作メモ.txt                  ← 未設定項目と確認範囲

仕上げ時には「最終チェック結果.md」や修正前後のキャプチャも受け取ります。配置は案件により変わります。移動するときは、HTML・CSS・画像の相対的な位置関係を保ちます。

GITHUB → NETLIFY

GitHubとNetlifyは、どうつながる？

GitHubは制作ファイルと変更履歴を保管する場所。Netlifyは、そのファイルから公開用のサイトを作り、インターネット上で配信するサービスです。

① パソコンで制作

HTML・CSS・画像を編集し、ローカルで表示を確認します。

② GitHubへ送る

変更をcommit（履歴として記録）し、push（GitHubへ送信）します。

③ Netlifyで公開

Git連携と自動公開が設定されていれば、対象ブランチの更新を受けてビルドし、公開用フォルダを配信します。

GitHubへのアップロードが、いつでも本番公開を意味するわけではありません。Netlifyとの連携、公開対象ブランチ、ビルド結果、公開フォルダの設定がそろって初めて公開につながります。

「ブランチ」と「本番公開」の関係

言葉意味・使い方
リポジトリGitHub上のプロジェクトの保管場所。HTMLや画像と変更履歴を管理します。
作業ブランチ変更を分けて進めるための履歴。このマニュアルは codex/lp-skill-manual-20261106 にアップしています。
Pull Request（PR）作業ブランチの変更を、別のブランチへ取り込むための提案。mergeすると変更が取り込まれます。
本番ブランチNetlifyが本番公開の対象にしているブランチ。main が使われる例はありますが、実際の設定を確認します。
Deploy Preview本番へ取り込む前に、PRの変更を確認するためのプレビュー。利用可否はNetlifyの設定によります。
ビルドソースから公開用ファイルを用意する処理。静的LPでは、必要なHTML・CSS・画像を公開フォルダへコピーするだけの構成もあります。
Publish directoryNetlifyが配信するフォルダ。リポジトリ全体がそのまま公開されるとは限りません。

このリポジトリの設定を読むと

netlify.toml には、ビルドコマンドが npm run build、公開フォルダが dist と記載されています。scripts/build-site.mjs が、指定されたLPやアプリのファイルを dist/ へコピーする構成です。

GitHubの対象ブランチを更新
        ↓ NetlifyのGit連携が有効な場合
npm run build
        ↓ scripts/build-site.mjs が実行される
dist/ に公開するファイルを用意
        ↓ ビルド・デプロイ成功
Netlifyの公開URLで表示

今回のマニュアルは、確認したビルドスクリプトではコピー対象に含まれていません。本番ブランチへ取り込むだけでは、このマニュアルの公開URLは作られません。公開する場合は、マニュアルと必要なリンク先を dist/ に含める設定も必要です。

ここで確認したのはローカルの設定ファイルです。Netlify管理画面の接続先・本番ブランチ・稼働状況は未確認です。この追記では、公開設定の変更や本番デプロイは行っていません。

公開まで進めるときの手順

  1. 対象リポジトリ・Netlifyプロジェクト・本番ブランチを確認する。
  2. 公開するLPと必要な画像・CSS・JSが、公開フォルダへ出力されるようにする。
  3. 作業ブランチへcommit・pushし、必要に応じてPRとプレビューで確認する。
  4. 公開する変更を本番ブランチへ取り込む。
  5. Netlifyのデプロイ結果と公開URLを確認し、画像・予約リンク・スマホ表示を確かめる。
公開まで依頼するときの例
対象LP：［フォルダ］
GitHubリポジトリ：［URL］
Netlifyプロジェクト：［名前または管理画面URL］
このLPをNetlifyで公開してください。
連携先・本番ブランチ・ビルドコマンド・公開フォルダを確認し、
既存の公開ページを保ったまま、必要なファイルを公開対象に含めてください。
GitHubへの反映と、Netlifyでの公開成功を別々に確認してください。
最後に公開URLと、スマホ・PC・画像・CTAの確認結果を教えてください。

GitHubに送ったのに表示が変わらないとき

  • Netlifyが、そのリポジトリ・ブランチと連携しているか。
  • 更新が本番ブランチに入っているか。作業ブランチだけの更新ではないか。
  • ビルドやデプロイが失敗・停止していないか。
  • 対象HTMLと画像が、公開フォルダに出力されているか。
  • ローカルのファイルや古いプレビューではなく、対象の公開URLを開いているか。

Git連携を使わず完成ファイルを手動でデプロイする方法もあります。その場合、GitHubへのpushと公開更新は自動では連動しません。更新方法を案件ごとにそろえておきます。

REVIEW

完成時に、自分でも確認すること

チェック欄はこの画面での確認用です。再読み込みするとリセットされます。

予約の実送信・予約確定・電話発信まで行う必要はありません。ローカルでの確認と、公開URLでの確認は別に記録します。

TROUBLESHOOTING

困ったときの依頼のしかた

何を渡せばよいか分からない

「原稿はこのファイル、テンプレートはこのフォルダです。足りない情報だけ教えてください」と依頼します。未確定の料金や実績を、AIに想像で埋めさせないようにします。

デザインの専門用語が分からない

「白を中心に、深いグリーンの予約ボタン。落ち着いた雰囲気。細部はおまかせ」のような文章で十分です。参考資料は「色を参考に」「余白を参考に」まで伝えると意図が伝わります。

テンプレートがまだない

「mobile-first-lp-template を使って、元の素材を残して新しいフォルダへLPの土台を作ってください」と依頼します。その後、完成原稿とデザインの希望を渡します。

原稿がまだ完成していない

流し込みの前に、掲載内容を整理します。サービス・対象・料金・条件・選ばれる理由・FAQ・店舗情報・予約先を確定し、根拠のない口コミ・実績・効果は追加しません。

FVやオファー画像も作りたい

完成LPのデザインシート、掲載文言、使う写真、用途を添えて別工程で依頼します。人物を生成する場合は、肌に不自然な模様・線・ノイズ・まだら・シミ状の質感を入れず、自然で滑らかな写真風の肌と指定します。

色を変えたのに画像内の色が変わらない

CSSの変更では画像に描かれた色や文字は変わりません。「この画像内の配色も調整したい」と対象画像を指定して依頼します。

仕上げで文章まで変わるのを防ぎたい

「原稿・料金・条件は維持。改行・余白・文字サイズ・画像配置のみ調整」と変更範囲を具体的に指定します。チェックだけなら「編集せず、問題箇所だけ報告」と伝えます。

直したい場所をうまく説明できない

「スマホ版の料金表で、メニュー名と価格の間隔を広げたい」のように、画面幅・セクション・現状・希望をセットで伝えます。修正後はその箇所の表示確認も依頼します。
