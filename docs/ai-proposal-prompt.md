# AILP AI proposal prompt

このファイルは、AILPがGA4データと現在のLP HTML/CSSから改善案を作るための提案プロンプト・判断ノウハウを管理する。クライアントと一緒に育てる前提で、判断基準、出力形式、採用・不採用理由をここに追記していく。

実装上の現在の呼び出し元は `VPS/src/worker/openai.js` の `createImprovementProposal()`。このmdは、そのプロンプトを育てるための原本として扱う。

## 目的

AIは単なる改善アイデアではなく、GA4の実績と現在のLP構造から、次に検証すべき改善方針を出す。提案はそのまま本番公開せず、管理画面で人が確認・編集し、draftで確認する。

AIが必ず判断すること:

- 数値上の主な課題は何か
- その課題はLP内改善で扱うべきか、別LPとして検証すべきか
- マクロ修正かミクロ修正か
- 現在のHTML/CSS上でどこを直すべきか
- 1回のdraftで検証できる現実的な範囲か
- 計測不備をLP改善と混同していないか

## 入力

AIに渡す入力はLP単位に限定する。他のLP、他クライアント、秘密情報、VPS内の不要ファイルは渡さない。

- LP概要
  - クライアント名
  - LP名
  - folder_path
  - public_url
  - GA4 page path
- GA4データ
  - 直近30日サマリ
  - 直近90日の合計
  - 流入 source / medium
  - sessions
  - users
  - page views
  - conversions
  - conversion rate
  - engagement rate
- 現在のLP構造
  - `index.html` のテキスト構造
  - 主要CTA文言
  - section id / class
  - 見出し
  - CTAリンクの数と位置
- CSSの状態
  - CTA、hero、section、responsiveに関係するCSS
  - 既存デザインのトーン

## マクロ修正とミクロ修正

管理画面では、改善案を大きく2種類に分ける。

### マクロ修正: 別LPを新規制作

マクロ修正は、現LPの細部ではなく、訴求軸・ターゲット・コンセプト・オファー・差別化を変えて検証する方針。現LPは維持し、別LPまたはdraft previewで新しい切り口を確認する。

マクロ修正に分類する条件:

- 内容は読まれているのにCVやCTAが弱い
- 現LPの構成を少し直すだけでは選ばれる理由が作れない
- ターゲットや訴求軸が曖昧
- 競合との差別化や価格価値が弱い
- 既存LPとは別の仮説を検証した方がよい
- 広告・SNSの訴求とLPの約束がずれている

マクロ修正で扱うもの:

- 誰向けのLPか
- 何を選ぶ理由にするか
- 競合との違い
- オファーや価格価値
- ファーストビューの約束
- LP全体の切り口

マクロ修正の出力では、`route` の意味を `macro` と考え、UIでは「別LP制作へ進める」と表示する。

### ミクロ修正: 現LPを細かく改善

ミクロ修正は、現LPの訴求軸は大きく変えず、構成・情報順・CTA・読みやすさ・不安解消を改善する方針。既存HTMLを壊さず、現在のLP上で検証できる範囲を優先する。

ミクロ修正に分類する条件:

- 主な訴求やターゲットは大きく外れていない
- CTA位置や文言が弱い
- 読了前後で不安解消が足りない
- 情報順や比較材料を整理すれば改善できる
- セクション単位の補強で検証できる
- デザインやブランドトーンは維持した方がよい

ミクロ修正で扱うもの:

- hero見出しやリード文
- CTA文言と補足
- CTA直前の不安解消
- 比較・選ばれる理由の追加
- FAQの補強
- 料金やオファーの見せ方

ミクロ修正の出力では、`route` の意味を `micro` と考え、UIでは「現LP改善へ進める」と表示する。

## GA4指標と提案理由の紐づけ

提案では、GA4指標を単に並べず、必ず「数値の事実 → ユーザー心理の仮説 → HTML上の該当箇所 → 改善案」の順で説明する。数値だけで断定せず、LP内の文言・CTA・セクション構造と照合して理由を作る。

### 指標別の読み取り方

- `sessions` / `users`
  - 事実: 流入量が十分か、少なすぎないかを見る。
  - 仮説: 流入が少ない場合、LP改善の良し悪しをCVだけで判断しにくい。
  - 提案理由: LP内改善より、広告・SNS・検索導線・計測確認を併記する。
  - HTML観点: ファーストビューの約束が流入元の訴求と一致しているかを見る。
- `page views` / `views per user`
  - 事実: 同じユーザーが複数回見ているか、ほぼ一回で終わっているかを見る。
  - 仮説: 複数回見られてCVしない場合、比較材料・価格価値・不安解消が不足している可能性がある。
  - 提案理由: CTA直前、料金、FAQ、選ばれる理由を優先する。
  - HTML観点: 中盤以降に納得材料があるか、CTA前に不安解消があるかを見る。
- `engagement rate`
  - 事実: 冒頭で興味を持たれているかを見る。
  - 仮説: 低い場合、対象者・悩み・得られる変化が最初に伝わっていない可能性がある。
  - 提案理由: hero見出し、リード文、冒頭CTA、悩み訴求の改善を優先する。
  - HTML観点: `hero` / first view の見出しが「誰に、何を約束するか」を言えているかを見る。
- `conversions`
  - 事実: 予約、LINE、電話、フォームなどの行動が発生しているかを見る。
  - 仮説: 0件の場合は、LPの問題と計測不備の両方を疑う。
  - 提案理由: 「CVが少ないからコピー変更」と短絡せず、イベント設定・リンク先・CTAクリック計測も確認対象に入れる。
  - HTML観点: CTAリンクが存在するか、CTA文言が行動内容と一致しているかを見る。
- `conversion rate`
  - 事実: 流入に対して行動率が低いかを見る。
  - 仮説: 読まれているのにCVRが低い場合、選ばれる理由・オファー・不安解消・CTA文言が弱い可能性が高い。
  - 提案理由: CTA周辺、料金前後、FAQ、比較・証拠の補強を優先する。
  - HTML観点: CTA前に「なぜ今相談するべきか」「相談すると何が分かるか」があるかを見る。
- `source / medium`
  - 事実: 流入元ごとの期待値を見る。
  - 仮説: Instagram、広告、検索、紹介ではユーザーの温度感が違う。
  - 提案理由: 流入元の文脈とLPのファーストビューがずれている場合はマクロ修正寄りにする。
  - HTML観点: 流入元の訴求とLP冒頭の言葉が一致しているかを見る。

### 提案理由の書き方

良い理由は、以下の4点を1セットで書く。

```text
GA4では〇〇が△△で、ユーザーは□□の段階で迷っている可能性がある。
現在のHTMLでは、該当箇所が◇◇にあり、CTA前に不足している情報は□□。
そのため、今回はhero/CTA/FAQのうち〇〇を優先して改善する。
この変更は次回GA4で□□指標を見て検証する。
```

避ける理由:

- 「CVRが低いのでCTAを改善」だけで終わる
- GA4指標とHTML上の場所が結びついていない
- 数値が少ないのに断定する
- 計測不備の可能性を無視する
- 流入元の期待値を見ずにheroだけ変える

### GA4からHTMLへの紐づけ例

| GA4の事実 | 仮説 | 優先するHTML箇所 | 提案例 |
| --- | --- | --- | --- |
| engagement rate が低い | 冒頭で自分向けだと伝わっていない | hero見出し / リード文 | 対象者と得られる変化をheroに明記する |
| 読まれているがCVRが低い | 納得材料はあるが行動前の不安が残る | CTA直前 / FAQ / 料金前 | 相談前に分かること、予約前の不安解消を追加する |
| page views があるがCVが少ない | 比較検討されているが選ぶ理由が弱い | 選ばれる理由 / 証拠 / before after | 競合との違い、施術後の変化、判断材料を補強する |
| conversions が0 | LP問題か計測不備か未確定 | CTAリンク / GA4イベント | CTAクリック計測とリンク先を確認し、HTML改善は小さく行う |
| sourceがSNS中心 | 短時間で判断される | first view / 画像周辺 / CTA | 冒頭にベネフィットと相談導線を短く出す |

### 提案に必ず含める検証指標

各recommendationには、期待効果だけでなく、次回見る指標を含める。

- hero改善: engagement rate、scroll、CTAクリック
- CTA改善: click event、conversion rate、CTA到達後の行動
- FAQ・不安解消: conversion rate、CTAクリック、ページ滞在
- 比較・証拠補強: engagement rate、scroll、conversion rate
- 計測確認: event count、conversion設定、外部予約リンククリック

## 改善案生成の基本姿勢

AIはプロのマーケターとして判断する。デザインや文章の好みではなく、数値から見える課題とLP上の該当箇所を結びつけて提案する。

良い提案の条件:

- GA4の事実と結びついている
- マクロ修正かミクロ修正かが明確
- 現在のHTML上のどこを変えるかが明確
- 実装範囲が現実的
- 1回のdraftで確認できる
- 本番公開前に良し悪しを判断できる
- 既存ブランド、トーン、導線を壊さない

悪い提案の例:

- 「CVRを改善しましょう」だけで具体箇所がない
- マクロ課題なのにボタン文言だけで済ませる
- ミクロ課題なのにLP全体を作り直す前提にする
- GA4から読み取れない断定をする
- 実装コストが大きすぎる
- デザイン思想を無視して派手な表現だけ足す
- GTMや計測未整備が原因なのにコピーだけ変える

## 改善判断の流れ

### 1. GA4から課題を分類する

まず数値を見て、課題を大きく分類する。

- 流入不足
  - sessionsが少ない
  - 広告・SNS・検索など流入チャネルの問題が強い
  - LP内改善だけで判断しすぎない
- 興味不足
  - engagement rateが低い
  - page viewsや滞在が弱い
  - ファーストビュー、訴求、対象者の明確さを疑う
- 読了不足
  - 中盤以降で離脱している可能性が高い
  - 長さ、順序、証拠、比較、料金前の納得材料を疑う
- 行動不足
  - 読まれているがconversionが弱い
  - CTA文言、CTA位置、予約前不安、オファー、フォーム導線を疑う
- 計測不備
  - conversionsが0または不自然
  - フォーム、LINE、電話、Hot Pepperなどのイベント設計を確認する

### 2. マクロかミクロかを決める

判断の目安:

- 読まれているが選ばれていない → マクロ寄り
- 冒頭で離脱している → マクロまたはheroミクロ。訴求軸が弱いならマクロ
- CTAだけ弱い → ミクロ寄り
- 料金前後で落ちる → ミクロ寄り。ただし価格価値の見せ方が根本的に弱いならマクロ
- 広告訴求とLPがずれている → マクロ寄り
- CVが0でクリック計測も不明 → 計測確認を優先

### 3. 現HTML/CSSから該当箇所を探す

見る場所:

- hero / first view
- CTAボタンとそのリンク
- 悩み訴求
- ベネフィット
- 実績・権威性
- before after
- 口コミ
- 比較表
- 料金
- FAQ
- 最後のCTA

判断例:

- CVが弱いのにCTAが下部中心なら、上部・中盤CTAを検討する
- engagementが低いなら、hero見出しと冒頭の対象者訴求を優先する
- 読了はあるがCVが弱いなら、料金前後と最後の不安解消を優先する
- クリックイベントがないなら、LP改善より計測確認を優先提案に含める

### 4. 変更案を優先順位付けする

1回のdraftでは最大3〜5件に絞る。多すぎると検証不能になる。

優先度の考え方:

1. マクロ / ミクロの分類
2. CV導線の明確化
3. ファーストビュー訴求
4. CTA直前の不安解消
5. 比較・選ばれる理由
6. 料金・オファーの見せ方
7. 計測不備の確認

## 提案の自己レビュー

最初の提案をそのまま採用しない。必ずもう一度見直す。

レビュー観点:

- マクロとミクロを混同していないか
- 限定的すぎないか
  - ボタン文言だけ、色だけ、1箇所だけの変更で終わっていないか
- 広すぎないか
  - 1回のdraftで検証できない全面改修になっていないか
- 現実的か
  - 今あるHTML/CSSでdraft反映できるか
- 検証可能か
  - 変更後にGA4で良し悪しを判断できるか
- 数値と対応しているか
  - GA4の事実から離れていないか
- 計測不備を無視していないか
  - CVが0の場合、まず計測確認も入れる
- 既存トーンを壊さないか
  - クライアントのブランドやLPの雰囲気に合っているか

レビュー後、採用する提案には `approved_for_draft=true` を付ける。落とした提案には理由を残す。

## 実プロンプトへ反映するときの注意

このmdを更新しただけでは、AIへの実プロンプトは変わらない。実プロンプトに反映する場合は `VPS/src/worker/openai.js` の `createImprovementProposal()` を更新する。

更新時は、以下を守る。

- LP単位の情報だけを渡す
- 他LPや他クライアントの情報を混ぜない
- route を `macro|micro|measurement` で出させる
- `target_area` と `target_selector_or_text` を必ず出させる
- 自己レビューと見送り案を出させる
- `ga4_evidence` / `html_evidence` / `reason_chain` / `validation_metric` を出させる
- GA4の数値が少ない場合は断定せず、仮説と計測確認を分ける
