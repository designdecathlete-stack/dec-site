# LPデザインの仕上げ・最終チェック

制作済みのLPを読みやすく、内容と行動先が伝わる状態に仕上げる。批評や改善案だけで終わらず、許可された範囲で修正し、実画面で再確認する。「チェックだけ」と指定された場合は編集せず、具体的な指摘を返す。新規LP制作や公開操作はこのスキルの目的ではない。

## 1. 対象と変更できる範囲を確定する

- 会話・指定ファイル・作業フォルダから対象LP、正本の原稿、デザインシート、採用画像、CTA設定を確認する。古い版や配布テンプレートと取り違えない。複数の有力候補が残る場合だけ対象を確認する。
- 既存HTML・CSS・JS・画像を読み、スマートフォンとPCで修正前を撮影する。画像内の文字も実際に見る。
- 指定された複製・バックアップ方針を守る。指定がなければ対象LPを編集し、変更前のファイルまたは差分を復元できる形で残す。不要な新規LPの量産やテンプレートの書き換えをしない。
- 変更禁止項目を記録する。原稿、金額、税込区分、メニュー、時間、適用条件、追加料金、期限、限定数、連絡先、リンク、ブランド色、採用画像は原則維持する。明示された変更指示があればそちらを優先する。
- 資料間に料金や事実の矛盾があれば、見栄えを理由に推測で統一しない。その箇所を保留し、独立したデザイン改善を進める。

## 2. デザインの課題を見極めて直す

以下を観察し、効果のある項目を選んで改善する。問題のない箇所まで変更して、作業量を増やさない。

### 第一印象と情報の強弱

- 最初の画面で業種・サービス・主な訴求が伝わるか。画像の上に不要な空白や重複する店名帯が積み重なり、主役が押し下げられていないか。
- 見出し・価格・補足に明確な強弱があるか。すべてを大きく太くせず、主役を絞る。既存の配色・トンマナでコントラストをつける。
- キャッチコピーの改行は意味のまとまりを保つ。一文字だけの行や、不自然な助詞の折り返しを整える。文章そのものを勝手に書き換えない。
- 文字入りFV・オファー画像とHTMLで同じ内容が連続していないか。視覚上の重複を整理しつつ、意味のある見出し・代替テキストまたは読み上げ用本文を残す。

### 読みやすさと余白

- 本文の行長、行間、見出し前後、セクション間の余白に一貫性を持たせる。余白を広くすること自体を目的にしない。
- 本文はスマートフォンで無理なく読める大きさを選ぶ。通常は16px前後を目安にし、既存の指定・実画面で調整する。重要条件を極端な小文字や低コントラストで隠さない。
- 背景・罫線・角丸・影・アイコンを整理し、情報の区切りに役立つ装飾だけを使う。新しいブランド色や過剰なアニメーションを無断で追加しない。
- 比較表・料金表・FAQの長い文が読めるか。モバイルで収まらない場合は読みやすい配置に調整し、項目や料金は削らない。

### 画像とCTA

- 写真の内容と掲載箇所が一致するか。同じ人物写真の不要な繰り返し、オーナー写真と口コミの取り違え、AI画像を実績に見せる扱いを修正する。
- 文字入り画像は原則width:100%、height:autoで全体表示。object-fit:cover等で文字・価格・条件を切らない。写真も目元・顔・重要な被写体を切りすぎない。
- 画像内の誤字・価格・小さすぎる条件はCSS変更では直らない。必要な画像修正を区別し、現在の依頼が許す範囲で画像生成ツールを使う。使えない場合は修正済みとせず、画像の残課題を示す。
- 人物画像の生成・編集では、自然で滑らかで清潔感のある肌を維持。不自然な模様・線・ノイズ・まだら・シミ状のテクスチャを入れない。
- CTAの見た目・文言・リンク先を役割ごとに統一し、押せる領域を確保する。異なる予約先が意図されている場合は一律に書き換えない。
- 画像化したCTAも実際のリンク要素内に置く。予約先が未設定なら設定を推測せず、未設定表示と既存の案内先を維持する。
- PC左右追従＋中央スマホ幅のLPでは、その構造を維持する。スマートフォンでは左右枠と固定CTAの切替を確認し、追従枠を本文やフッターに重ねない。

## 3. 原稿・機能を照合する

デザイン修正の前後を比較し、次を確認する。

- 本文・画像内・右追従枠・メニュー・最後のオファーで、通常価格／初回価格／対象／時間／追加料金／適用条件が矛盾しない。表示場所に応じた短縮は、必要な詳細条件へ到達できることを確認する。
- 口コミ・事例・資格・数値・効果を追加しない。架空サンプル、AI生成、個人差等の既存注記と必要な条件を残す。
- 予約URL・電話・地図・フォーム・計測コードを維持する。リンク設定の一元管理がある場合はその仕組みを使う。
- アンカー先とナビ項目、画像の相対パス、大文字小文字、alt、h1、ページタイトル、meta descriptionを確認する。文字入り画像でも見出し構造を放棄しない。
- 外部サービスへの実送信・予約確定・電話発信はしない。CTAは設定と遷移先を確認する範囲にとどめる。

既存のlp-quality-checkerが利用できる場合、その静的チェッカーを補助に使ってよい。必須依存にはせず、未導入でもファイルとブラウザでチェックする。静的検査の合格だけを視覚確認済みとしない。

## 4. ブラウザで最終確認する

最低限、幅375px程度のスマートフォンと1366px程度のPCで最終画面を開く。レイアウト切替を変更した場合は境界前後も確認する。

- FVだけでなく、オファー、本文、比較表、料金、FAQ、最後のCTAまでスクロールして実画面を見る。
- 横はみ出し、文字欠け、画像の切れ、不要な空白、文字と写真の重なり、固定CTAによる末尾の隠れがないか。
- 画像がすべて読み込め、最終採用した版を参照しているか。文字入り画像は375px表示で条件まで読めるか。
- 左ナビ移動と現在地、右枠追従、FAQ開閉、CTA遷移、キーボードフォーカスが機能するか。
- コンソールエラーと失敗したリソース要求を調べる。無関係な外部要因と今回の不具合を分ける。
- 修正した箇所を再確認し、重大な残課題がないところで完了する。新たな問題が出ていない限り、際限なく再設計や再テストを繰り返さない。

ブラウザが使えない場合は静的確認まで進め、表示・動作を未検証と記録する。「すべて問題なし」「公開可能」と断定しない。

## 5. 引き渡し

- LPの隣に短い「最終チェック結果.md」を保存する。主な変更と理由、確認した画面幅・機能、原稿と料金の照合結果、残課題を記載する。
- 修正前後の代表スクリーンショットをLPの公開フォルダ外へ保存する。内部資料を顧客向け画面へ混ぜない。
- 既存のデザインシートがあり、今回の変更で実装とズレた場合はHTML・画像・設定値を対応する範囲で更新する。更新できなければ古い状態であると明記する。
- 結果は「確認済み」「要修正」「未検証」「未設定」を区別する。架空サンプルの未設定予約URLを、実予約まで動作確認済みとしない。
- 最終報告は完成LPのプレビュー、主な改善点、確認範囲、重要な残課題を簡潔に示す。改善点がなければ不要な変更をせず、その旨を伝える。
- ユーザーが別途依頼していない公開・デプロイ・Git commit/pushは行わない。ローカル確認と公開サイト確認を区別する。
