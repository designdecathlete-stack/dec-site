# LP原稿の流し込み・デザイン反映・デザインシート画像出力

完成原稿と既存テンプレートから、ブラウザで確認できるLPを作る。原稿の意味と条件を守り、ユーザーが指定した配色・雰囲気を反映する。仕上げとして、実際のLPの見た目を正本にしたデザインシートを画像で出力する。後から作るファーストビュー・オファー画像・別ページのトンマナ合わせに使える納品物とする。

制作済みLPからデザインシートだけを作る依頼では、既存LPを読み取り、工程5の必要な表示確認と工程6を行う。原稿の再提出やLPの作り直しは求めない。

## 1. 原稿・テンプレート・デザイン指定を受け取る

最初に会話、添付ファイル、指定フォルダを確認する。すでに渡されたものを再提出させない。足りない入力だけを、まとめて短く尋ねる。

基本の案内例（未提供の項目だけ残す）：

> LPに反映する原稿と、使用するテンプレートのフォルダまたはZIPをご指定ください。
> 配色・デザインは、次のいずれかでお伝えください。
> ・記入済みのデザインシートを添付する
> ・参考画像やブランド資料を添付し、取り入れたい部分を伝える
> ・希望の色や雰囲気を文章で伝える
> 未定の項目は「おまかせ」で構いません。

添付を求める場合は通常のチャットで案内する。テキスト回答しか扱えない質問ツールでファイル添付を依頼しない。

- 原稿：テキスト・Word・PDF・会話内の完成原稿など。ラベルや制作メモと、実際に掲載する文章を区別する。
- テンプレート：対象を特定してHTML・CSS・JavaScriptと画像の構成を読む。ZIPは別の作業フォルダに展開し、元ファイルを保つ。候補が複数あれば選択を確認する。
- デザイン指定：添付シート、ブランド資料、参考画像、文章指定のいずれでもよい。所定シートの利用を必須にしない。
- 参考画像は実際に表示して確認する。URLが指定された場合も実物を確認し、色・書体・密度・余白など、どこを参考にするかを整理する。
- 不足した必須入力がある間も、渡された原稿の章立てやテンプレートの構造を整理できる。原稿や制作対象を推測して作業しない。

入力用の記入シートは任意であり、完成後に作る画像のデザインシートとは区別する。記入用シートは [assets/design-sheet.txt](assets/design-sheet.txt) を使う。架空サロンの記入例は [assets/design-sheet-example.txt](assets/design-sheet-example.txt) にある。ユーザーがシートを必要としているときにコピーして渡す。例の配色をすべての案件の既定値にしない。

## 2. デザイン方針を整理する

決める項目は次のとおり。色番号がなくても「深いグリーン」「やわらかい雰囲気」などから具体化できる。

- メインカラー・CTA色・CTA文字色・背景色・本文色
- 雰囲気（落ち着いた、明るい、やわらかい等）と避けたい表現
- 見出しと本文の書体、余白、角丸、線や影の強さ
- 参考資料の取り入れる部分と、踏襲しない部分
- ロゴ、写真、生成済み画像の用途と掲載位置

ユーザーの明示的な指定を優先し、参考資料は指定の範囲で利用する。指定同士の重要な矛盾は確認する。「おまかせ」の項目は原稿と参考資料に合う値を選び、採用内容を短く伝えて制作に進む。全項目の再承認を既定の工程にしない。

デザイン指定がまったくなく、おまかせの許可もない場合は、デザインの受け取り方法を先に確認する。経過時間を承認として扱わない。

## 3. 元のテンプレートを複製して原稿を配置する

配布テンプレートへの流し込みでは、元を残して店舗・サービス別の出力フォルダを作る。既存LPの修正を明示された場合は、その対象を編集する。

テンプレートの実際の構造に合わせて、原稿を以下の掲載箇所へ対応付ける。原稿順とHTML順が違っていても、意味に合う場所に配置する。

| 原稿の内容 | 配布テンプレートの主な配置先 |
| --- | --- |
| 店名・サービス概要・キャッチコピー | title、meta description、ヘッダー、ファーストビュー、フッター |
| 初回メニュー・価格・条件 | #offer、右追従枠、料金表、最後のオファー |
| 顧客の悩み | #problem |
| コンセプト・オーナー紹介 | #concept |
| 選ばれる理由 | #reason |
| 施術事例・口コミ | #proof、#voice |
| 比較内容 | #comparison |
| ご利用の流れ | #flow |
| メニューと料金 | #menu |
| よくある質問 | #faq |
| 店舗情報・地図 | #access |
| クロージング | #reservation |

- 原稿の項目数に合わせてカード・FAQ・事例を増減する。テンプレートにある件数へ無理に削らない。
- 価格、通常価格、対象、所要時間、含まれるもの、追加料金、期限、限定数を勝手に変更・追加しない。異なる記載があれば確認する。
- 追従オファー用の短縮原稿があれば使う。なければ重要条件を保って短縮し、詳細条件へ到達できるようにする。
- CTAは指定された文言・リンク先に統一する。複数の行動先が明示されている場合はその意図を保つ。
- 制作メモ、ファイル名、色番号、ヒアリング質問を顧客向け本文へ混ぜない。架空事例・口コミに付く「制作サンプル」の注記は削除しない。
- 比較表が「確認ポイントと自店の対応」で提供されている場合、実在他店との比較へ書き換えない。
- 不明な情報を捏造しない。未設定の予約先・地図は仮枠のまま残し、実在店舗のURLや場所を推測で設定しない。
- セクションを削除・改名したときは左メニューとアンカーも同期する。

## 4. 配色・デザインを反映する

- 既存CSSの変数を確認し、主要色を冒頭の `:root` に集約する。配布テンプレートなら `--brand`、`--on-brand`、`--text`、`--muted`、`--page`、`--soft`、`--canvas`、`--line` を更新する。
- メインカラーとCTA色を別に指定された場合は `--cta` と `--on-cta` 等を追加し、必要なボタンへ適用する。リンク、開閉UI、追従枠まで色を統一する。
- スマートフォンを基準に、長い見出し・価格・条件が読める行長と余白にする。装飾のために本文を画像化しない。
- PCは中央約480pxのLPを維持し、左に追従メニュー、右にオファーとCTAを配置する。スマートフォンでは左右を隠して下部固定CTAを表示する。ユーザーの別指定があればそちらを優先する。
- 参考画像を指定されても、無断でその画像内の写真やロゴを素材として切り出さない。提供された使用素材だけを挿入する。
- ファーストビュー画像が未完成でも、原稿の流し込みと配色は進める。写真枠を残し、画像生成は依頼があった場合に別工程で行う。
- 文字入りの完成画像を使う場合、画面上の重複コピーを除き、意味のあるh1と代替テキストを残す。文字を含む画像をトリミングしない。
- オファー画像とCTA画像は役割を区別する。CTA画像は予約先リンクの中に入れ、既存のリンク共通設定を維持する。
- CSSの色変更では既存画像内の色は変わらない。画像側の調整が必要な場合は残作業として明示する。

## 5. LPの設定・表示を確認する

既存の設定機構を利用する。配布テンプレートの `script.js` には `reservationUrl`、`googleMapsEmbedUrl`、`googleMapsUrl` がある。Googleマップの共有リンクと埋め込みURLを取り違えない。

最低限、375px程度のスマートフォン幅と1366px程度のPC幅でブラウザ表示を確認する。構造チェックだけで視覚確認済みとしない。

- 文字・画像の欠けや横はみ出し、固定CTAによる末尾の隠れがない。
- 左メニューの移動と現在地、右オファーの追従、FAQの開閉が機能する。
- 料金・条件・CTAが本文・追従枠・固定ボタンで整合する。
- 予約先を未設定のままにした場合は、その状態が明確になっている。
- 画像のパスと読み込み、ボタン文字の読みやすさを確認する。
- 顧客向け原稿に未置換の「サロン名」「○○」などが残る場合、箇所と理由を報告する。

## 6. 実際のLPから、画像のデザインシートを作る

LPの表示確認後、追加依頼を待たずに `design-sheet.png` を作る。入力用テキストシート、色番号の一覧、全ページを縮小したスクリーンショットだけで完了しない。色と使い方、文字、部品、画面の雰囲気がひと目で分かる1枚の画像にする。

### 情報の抽出

最終LPのCSSとブラウザの計算済みスタイルを読み、採用済みの値を取得する。入力シートの希望値と実装が違う場合は、実装されたものを記録する。状態を「制作済みLPに基づくシート」と明記し、未承認なのに「承認済み」と書かない。

- 店名・案件名・作成日・対象LPのファイル名。
- メイン色、CTA色と文字色、背景色、補助背景、本文色、補足文字色、罫線。実際の色面に役割名とHEX値を併記する。
- 見出し・本文・補足・価格の文字見本。font-family、サイズ、太さ、行間の実際の指定を記録し、スマートフォン表示を基準にする。フォント候補の列挙と実際に読み込まれたフォントを混同しない。
- CTA、見出し、カード、価格・オファーなどの実物に基づく部品見本。角丸、線幅、余白も添える。
- 実際のスマートフォン版LPのファーストビューと代表セクションを1〜2点、読める大きさで配置する。フルページ画像を細長く縮めて代用しない。
- デザインを表す言葉を2〜3語。別素材で守るルールを3〜5個（例：背景は白を中心にする、CTAは深い緑、影を控える）。明示的な指定と、LPを観察して言語化した方針を区別する。
- 写真がある場合は色温度・明るさ・構図等の方向性。画像が仮枠なら「写真未確定」と明記し、仮枠を完成デザインの写真として紹介しない。

### 画像の作り方

文字・HEX値・色面・実際のUIの正確さを優先し、HTML/CSSでシートを組み、ブラウザでPNGを書き出す方法を基本とする。これは指定値と画面を正確に見せる画像制作であり、AIで新しいデザイン案を描き直す工程ではない。

レイアウトと出力時の確認事項は [references/design-sheet-layout.md](references/design-sheet-layout.md) を読む。

1. 最終LPを表示し、375px程度の幅でファーストビューや必要な部品を撮影する。フォント・画像の読み込みとアニメーションの完了を待つ。
2. シートのHTMLを作り、色面・書体見本・部品・実画面・使い方のルールを配置する。実画面のキャプチャと色面が対応しているか確認する。
3. 画像は原則1600×2000px程度、sRGB相当の通常のPNGとする。重要文字は最終画像上で24px程度以上を目安にする。情報量に合わせて高さを調整し、無理に文字を小さくしない。
4. 書き出したPNGを実際に開き、文字欠け、画面のつぶれ、色番号の誤記、部品と実装の不一致を確認する。
5. 編集可能なシートHTMLと、正確な設定値・再利用ルールを記録した `design-tokens.json` を一緒に保存する。必要なキャプチャは相対パスで含める。

ユーザーがAI生成のムードボードも求めた場合だけ、それを追加で作る。色番号や実際のUIを保証するデザインシートは、生成された想像図に置き換えない。人物画像を新たに生成するときは自然で滑らかな清潔感のある肌にし、不自然な模様・線・ノイズ・まだら・シミのようなテクスチャを入れない。

### 後工程への引き継ぎ

`design-tokens.json` は対象LP、作成日、画面幅、色の役割と値、書体設定、部品の数値、画像の方向性、未確定事項を記録する。別ページや画像を作るときは `design-sheet.png` を見た目の参照に、JSONを正確な値の参照に使う。

## 7. 納品

制作フォルダとデザイン資料を分け、公開用LPに内部メモを混ぜない。構成例：

- `lp/`：静的HTML・CSS・JavaScript・画像。
- `design/design-sheet.png`：添付して使えるトンマナ共有用画像。
- `design/design-sheet.html`：編集・再出力用シート。
- `design/design-tokens.json`：配色・書体等の正確な設定。
- `design/assets/`：シートが参照するLPキャプチャ。
- `制作メモ.txt`：未設定事項や確認範囲。

完成報告ではLPのプレビューと出力先に加え、デザインシート画像を表示し、画像へのリンクを渡す。採用した配色、確認した範囲、残る画像・URL等を簡潔に伝える。

配布用ZIPを求められた場合は制作物と資料をまとめ、公開対象が `lp/` であると案内する。資料一式の相対パスも確認する。流し込みの依頼だけで公開・Git pushを行わない。
